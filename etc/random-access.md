# 랜덤액세스

## NL조인에서 랜덤액세스가 비효율적인 이유

- **"하나씩 다 찾는 시퀀셜(Sequential)보다 바로 찍어서 가져오는 랜덤(Random)이 더 빠른 거 아냐?"** 라고 생각할 수 있습니다.
- 하지만 데이터베이스 성능 관점에서의 **'비효율'** 은 **"한 번 움직일 때 얼마나 많은 일을 하느냐"** 라는 효율성의 문제입니다.
- 왜 NL 조인의 랜덤 액세스가 대량 데이터에서 비효율적인지, 시퀀셜 액세스(Full Scan)와 비교하여 설명해 드릴게요.

#### 1. '한 건'을 위해 '한 블록' 전체를 읽는 비효율

> * 시퀀셜: 마트에서 카트를 밀며 진열대 줄을 따라 필요한 물건을 몽땅 담는 것. (이동은 많지만 한 번에 많이 담음)
> * 랜덤: 물건 딱 하나 살 때마다 주차장에서 매장까지 왕복하는 것. 100개 사려면 100번 왕복해야 합니다. 물건이 적을 땐 빠르지만, 많아지면 최악이 됩니다.

- 데이터베이스는 데이터를 읽을 때 '레코드 하나' 단위로 가져오지 않고, 여러 레코드가 담긴 '블록(Block) 혹은 페이지(Page)' 단위로 읽어 메모리(버퍼 캐시)에 올립니다.

- 시퀀셜 액세스(Full Scan)
	- 한 블록을 읽으면 그 안에 있는 수십~수백 개의 레코드를 한꺼번에 다 처리합니다. 
	- "한 번의 I/O로 대량 수확"을 하는 셈입니다.
- NL 조인의 랜덤 액세스
	- 드라이빙 테이블에서 찾은 값 하나를 가지고 후행 테이블의 인덱스를 타고 내려가서, 실제 데이터 블록 하나를 읽습니다. 
	- 그런데 그 블록 안에 레코드가 100개 들어있어도, 딱 1개만 쓰고 버립니다. 
	- 그리고 다음 데이터를 위해 또 다른 블록(혹은 같은 블록을 다시)을 랜덤하게 찾아갑니다.

#### 2. I/O 방식의 차이 (Single vs Multi Block)
- 하드웨어 수준에서의 속도 차이도 큽니다.
 
- 시퀀셜 (Multi-Block Read)
	- "이 줄 다 읽을 거야"라고 미리 알려주기 때문에, OS와 디스크가 인접한 블록들을 한꺼번에 미리 읽어들입니다(Prefetch).
- 랜덤 (Single-Block Read)
	- "어디로 튈지 모르는" 접근 방식이라 한 번에 딱 한 블록씩만 요청합니다. 
	- 매번 디스크 헤더가 움직이거나 메모리 주소를 새로 계산해야 하므로 오버헤드가 큽니다.

#### 3. 메모리 경합 (Latch와 Lock)
- 메모리에 블록이 있더라도 문제입니다. 
- 랜덤하게 메모리(Buffer Cache)를 뒤질 때마다 **"내가 이 블록 쓸 테니 건들지 마"** 라는 일종의 잠금 장치(Latch)를 걸어야 합니다.

- 데이터가 수만 건, 수백만 건이면 이 '찾고 잠그는' 행위 자체가 CPU에 엄청난 부하를 줍니다.
- 반면 해시 조인(Hash Join)이나 소트 머지 조인(Sort Merge Join)은 대량의 데이터를 일단 메모리에 쏟아붓고 순차적으로 처리하므로 이런 자잘한 통행세가 훨씬 적습니다.

| 구분 | 랜덤 액세스 (NL 조인 위주) | 시퀀셜 액세스 (Full Scan 위주) |
|---|---|---|
| 적합한 상황 | 추출 결과가 적을 때 (OLTP) | 추출 결과가 많을 때 (Batch/DW) |
| 효율성 | 필요한 것만 콕 집어와서 빠름 | 하나씩 읽을 때 비용은 싸지만 다 읽어야 함 |
| 비효율 원인 | 반복적인 I/O 호출과 블록 낭비 | 불필요한 데이터까지 읽어야 함 |

> 결론적으로 **"데이터가 적으면 랜덤 액세스가 압승이지만, 조인해야 할 대상이 많아지면 차라리 한 줄로 쭉 서서 한꺼번에 읽는 시퀀셜 방식(해시 조인 등)이 훨씬 경제적이다"**
